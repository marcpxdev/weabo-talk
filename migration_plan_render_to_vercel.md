# Migration Plan: Render → Vercel

## Overview

This document outlines the migration of WeaboTalk from Render (current deployment platform) to Vercel for deployment. The migration involves moving from a Docker-based Render service to Vercel's serverless deployment platform.

## Current State

### Current Deployment (Render)
- **Platform**: Render (Docker web service)
- **Database**: Supabase Postgres (external)
- **Storage**: Supabase Storage (external)
- **Runtime**: Ruby 4.0.0 + Rails 8.1.2 + Puma behind Thruster
- **Configuration**: `render.yaml` file with 60+ environment variables
- **Dockerfile**: Custom Dockerfile for Rails app

### Key Configuration Files
- `render.yaml` - Render deployment configuration
- `Dockerfile` - Docker container configuration
- `bin/docker-entrypoint` - Database setup script
- `.mcp.json` - MCP server configuration

## Migration Strategy

### Why Vercel?

Vercel offers several advantages over Render:
- **Native Node.js/Ruby support**: Vercel has official Ruby on Rails support
- **Global CDN**: Automatic edge caching and global distribution
- **Developer experience**: Better preview deployments and git integration
- **Cost efficiency**: Pay-as-you-go model with free tier
- **Simplicity**: Fewer moving parts compared to Render's Docker setup

- **Broadcasting**: Through `Notification` model callbacks

  - File: `app/services/notifications/comment_notifier.rb` - creates notifications
  - File: `app/jobs/comment_notification_job.rb` - enqueues notification processing

**Technical Implementation Details:**

```ruby
# Connection: app/channels/application_cable/connection.rb
module ApplicationCable
  class Connection < ActionCable::Connection::Base
    identified_by :current_user

    def connect
      self.current_user = find_verified_user
      logger.add_tags 'ActionCable', current_user.id
    end

    protected

    def find_verified_user
      if verified_user = env["warden"].user
        verified_user
      else
        reject_unauthorized_connection
      end
    end
  end
end
```

```ruby
# Model: app/models/comment.rb
class Comment < ApplicationRecord
  after_create_commit :enqueue_notify_post_author
  
  def enqueue_notify_post_author
    CommentNotificationJob.perform_later(id)
  end
end
```

```ruby
# Service: app/services/notifications/comment_notifier.rb
module Notifications
  class CommentNotifier
    def initialize(comment)
      @comment = comment
      @post = comment.post
      @recipient = @post.user
      @actor = comment.user
    end

    def call
      return if @actor == @recipient

      Notification.create!(
        user: @recipient,
        notification_type: "comment_created",
        notifiable: @comment
      )
    end
  end
end
```

```javascript
// Client: app/javascript/controllers/notification_controller.js
export default class extends Controller {
  connect() {
    this.subscription = ActionCable.createConsumer().subscriptions.create(
      {
        channel: "NotificationsChannel"
      },
      {
        received: this.handleNotification.bind(this),
        connected: () => console.log("Notification channel connected")
      }
    )
  }

  handleNotification(data) {
    this.updateNotificationCount()
    this.addNotificationToDOM(data)
    this.showNotificationToast(data)
  }
}
```

**Migration Challenges:**

1. **Vercel's Serverless Nature**:
   - No persistent WebSocket connections in edge functions
   - Connections are ephemeral (last ~30 seconds)
   - Cannot maintain state across requests

2. **State Management**:
   - Action Cable requires persistent connections
   - Need alternative for real-time communication
   - Must consider polling for frequent updates

3. **Implementation Complexity**:
   - Requires custom WebSocket server or polling
   - Need to handle connection lifecycle
   - Consider infrastructure requirements

**Possible Solutions:**

**Option 1: Custom WebSocket Server**
- Deploy separate WebSocket service (Redis-backed)
- Pros: Full control, supports persistent connections
- Cons: Complex deployment, additional infrastructure

**Option 2: Polling-Based System**
- Replace WebSocket with REST API polling
- Pros: Simple, works on Vercel
- Cons: Higher resource usage, less real-time

**Option 3: Vercel WebSocket Support**
- Use Vercel's limited WebSocket capabilities
- Pros: Serverless, managed
- Cons: Limited functionality, scaling concerns

**Option 4: Hybrid Approach**
- Use polling for most notifications
- Use WebSocket for high-frequency updates
- Pros: Balanced approach
- Cons: Complex implementation

#### 1.2 Vercel Platform Selection

**Platform Options:**

1. **Vercel for Rails** (Recommended)
   - Native Ruby/Rails support via `@vercel/ruby` buildpack
   - Automatic Node.js runtime selection
   - Built-in asset optimization
   - Global CDN deployment
   - **Best for**: Standard Rails applications

2. **Vercel + Custom Runtime**
   - Use custom Docker image if complex dependencies
   - More control over runtime environment
   - **Best for**: Applications with custom runtime needs

3. **Vercel Serverless Functions**
   - For API endpoints or specific functionality
   - Not recommended for entire Rails app
   - **Best for**: Microservices or specific endpoints

**Technical Decision Matrix:**

| Factor | Vercel for Rails | Custom Runtime | Serverless |
|--------|------------------|----------------|------------|
| Setup complexity | Low | Medium | High |
| Performance | High | High | Medium |
| Cost | Medium | High | Low |
| Maintenance | Low | Medium | High |
| WebSocket support | Limited | Full | None |

**Platform Selection Criteria:**

**Choose Vercel for Rails if:**
- ✅ Standard Rails application with typical gems
- ✅ No complex runtime requirements
- ✅ Ready to accept limitations on real-time features
- ✅ Want rapid deployment with minimal setup

**Choose Custom Runtime if:**
- ✅ Complex dependencies requiring specific runtime versions
- ✅ Need full control over the environment
- ✅ Have existing Docker setup (current Render setup)
- ✅ Require WebSocket persistence
- ✅ Have specialized monitoring/observability needs

**Choose Serverless Functions if:**
- ✅ Want to refactor monolithic app into microservices
- ✅ Have specific API endpoints that can be extracted
- ✅ Want to reduce operational overhead
- ✅ Accept performance trade-offs for cost savings
